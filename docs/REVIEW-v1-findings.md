## [high] session-1: Engine-creation failures hang forever: VadSegmenter.dispose awaits close() on a stream nobody listens to
- File: `lib/session/meeting_session_controller.dart:546`
- Scenario: VadSegmenter._out is a single-subscription StreamController (vad_segmenter.dart:101), and dispose() does `await _out.close()` (line 289). If the stream was never listened to, close() never completes (checked with dart run: close() on an unlistened controller times out). Three paths dispose a segmenter that has no listener: (a) SherpaSessionEnginesFactory.create catch (line 546), reached when segmenter.initialize() throws on a corrupt VAD model, ProcessingIsolate.spawn throws on a Whisper load error or OOM, or the Deepgram initialize() fails; (b) the start() catch at line 1464, when speakers.getAll / meetings.create / recordingsDir / setAudioPath throws before _listen(s); (c) reprocessFromAudio at post_processor.dart:950, through create(). In (a) and (b) start() never returns. The state stays `preparing` (isActive == true) and the recording screen shows a full-screen _BusyOverlay with no cancel button, so the user cannot record again until the app restarts. Because segmenter.dispose() never returns, the cloud engine or processor is never disposed either. In (c) MeetingJobsController._running never clears, so every later job on that meeting returns the same pending future.
- Fix hint: In VadSegmenter.dispose, do not await close() when `!_out.hasListener` (call close() unawaited or use a sync/broadcast controller). Or add a short timeout to that await.

## [high] session-2: reprocessFromAudio replaces the complete transcript with a partial one when some segments fail
- File: `lib/session/post_processor.dart:1028`
- Scenario: The only checks before the delete+insert transaction (1043-1049) are `collected.isEmpty && failedCount > 0` and `segmenterError != null && collected.isEmpty`. Example: Deepgram cloud ASR, and the network drops halfway through re-processing a 1-hour meeting. The first 30 minutes give segments; the rest fail and only count toward failedCount. collected is not empty, so the old full transcript (including manual text edits) is deleted and replaced by the half-transcript. Voiceprints are also unlearned for the old segments. The job then reports success with a notice, although the docstring says 'On failure the old transcript is kept'. A VAD error part-way through (segmenterError set, collected non-empty) loses data in the same way.
- Fix hint: Abort without touching the DB when failedCount > 0 or segmenterError != null (or when failedCount exceeds a small threshold), or ask for confirmation. Keep the old transcript and report the failure count.

## [medium] session-4: No backpressure in the live pipeline: unbounded backlog memory and a drain on stop that cannot be skipped
- File: `lib/session/meeting_session_controller.dart:667`
- Scenario: SessionPipeline.submit is called for every VAD segment with no capacity limit; waitForCapacity is used only by reprocess. Each submitted segment's samples are copied into a TransferableTypedData for the worker queue and also kept on the main isolate by the `_apply(segment, outcome)` closure until applied. Example: a large Whisper model on a mid-range phone with RTF > 1 over a 2-hour meeting builds a backlog of tens of minutes of audio, i.e. hundreds of MB held twice. That risks an OOM kill. On stop, _stop awaits pipeline.drain() under a modal overlay with no way to finish early; the only escape, cancel(), deletes the meeting. isProcessingBehind only shows a hint.
- Fix hint: Bound the pending audio (for example, beyond N minutes keep only the WAV archive and mark the remainder for reprocessFromAudio), or offer 'finish later' on stop: skip the drain, keep the transcript so far and mark the meeting for reprocessing.

## [medium] session-5: cancel() is not guarded against an in-flight stop(), so discard and an automatic stop race

## [low] session-7: learnFromCorrections treats any vanished previous speaker as a merge, so later corrections are never learned
- File: `lib/session/post_processor.dart:652`
- Scenario: When ledger[s.id] names a speaker that no longer exists and cur != null, the code assumes a merge, rewrites the ledger to cur and skips learning. A plain delete also produces this state. Example: the user deletes speaker X from the Speakers screen (FK sets the segments' speaker to null; no learning runs), then reassigns X's former segments to speaker Y. reassignSegment calls learnFromCorrections, which sees prev = X (missing) and cur = Y. It records the segment as Y's in the ledger without adding the embedding, so Y's voiceprint never learns from these explicitly locked corrections, and later runs see prev == cur and skip them forever.

## [low] session-8: Isolate respawn: in-flight segments are not retried after a Dart-level worker death, and dispose during a respawn leaks the new worker
- File: `lib/session/meeting_session_controller.dart:284`
- Scenario: ProcessingIsolate's _errorPort listener (processing_isolate.dart) calls _failAll before the _exitPort listener sets _dead. With errorsAreFatal, the error message arrives first, so `_runIsolate`'s catch sees `!iso.isClosed` and rethrows, and the segments queued in the dead worker fail instead of being retried as documented. Separately, if dispose() runs while `_respawning` is pending (stop or cancel shortly after a crash), it disposes the old _isolate, and the fresh worker (with a Whisper model loaded) is assigned afterwards and never disposed.
- Fix hint: Mark the isolate dead (or isClosed) in the error-port handler before failing pending work. In dispose(), await `_respawning` and dispose the result, and make _respawn refuse to run once disposed.

## [high] speech-ffi-1: VadSegmenter.dispose() never completes if nobody ever listened to `segments`
- File: `lib/speech/vad_segmenter.dart:289`
- Scenario: `_out` is a single-subscription StreamController, and dispose() does `await _out.close()`. That future only completes once the done event reaches a listener, so with no listener it waits forever (checked with a scratch Dart script: `StreamController<int>().close()` still had not completed after a 2 s timeout). In SherpaSessionEngineFactory.create (meeting_session_controller.dart:514-547) the segmenter is initialised before anyone listens. If ProcessingIsolate.spawn fails, the catch block runs `await segmenter.dispose()` and hangs. Spawn can fail with a Whisper initError: corrupt files, or not enough RAM for turbo/medium on a low-memory phone. cloud.initialize() can also throw MissingApiKeyException, and segmenter.initialize() can throw on a corrupt VAD model. In every case the original exception is never rethrown, and start() stays on the loading-models step with no error shown. The same hang happens in start() (meeting_session_controller.dart:1464) when anything fails between engine creation and `_listen(s)`.
- Fix hint: In dispose(), don't await close() when there is no listener: `if (_out.hasListener) { await _out.close(); } else { unawaited(_out.close()); }`. Or close without awaiting and let the done event go out on its own.

## [medium] speech-ffi-2: Timeout fallback kills the worker without freeing the native models and returns before it has exited
- File: `lib/speech/processing_isolate.dart:355`
- Scenario: dispose(waitForPending:false) waits 60 s for 'disposed'. If it does not arrive, it calls `_isolate.kill(priority: Isolate.immediate)` and returns straight away. Isolate.kill cannot interrupt a synchronous FFI call. A 29 s segment on whisper-medium or turbo can take more than 60 s to decode on an older phone or a busy Windows laptop (OfflineRecognizer.decode is one blocking FFI call). The worker keeps decoding and is then torn down without running shutdown(). OfflineRecognizer.free() and SpeakerEmbeddingExtractor.free() never run, so hundreds of MB to over 1 GB of ONNX Runtime memory is leaked until the app restarts. Because dispose has already returned, the next session or post-processing run spawns a second worker that loads Whisper again while the first copy is still resident. Peak memory roughly doubles, which leads to OOM kills on mobile.
- Fix hint: After kill(), await the exit signal (the _exitPort message) before returning, so callers cannot overlap a new model load. Better still, avoid killing: send 'dispose' with drain:false and wait without a timeout (decode cannot be interrupted anyway). If you must time out, record that native memory was leaked and refuse or delay respawning.

## [low] speech-ffi-3: Uncaught worker error fails pending segments before the isolate is marked dead, so they are never retried
- File: `lib/speech/processing_isolate.dart:261`
- Scenario: The isolate is spawned with errorsAreFatal at its default of true. An uncaught error first arrives on _errorPort, and its handler calls `_failAll(err)` but does not set `_dead` or `_closing`. The exit message is handled later as a separate event. The awaiting IsolateSegmentProcessor._runIsolate catch block (meeting_session_controller.dart:289) runs in a microtask before that event, sees `iso.isClosed == false`, and rethrows instead of respawning. Every segment in flight when the worker crashed is lost for good: no transcript and no voiceprint. Only later segments trigger the respawn.
- Fix hint: Set `_dead = true` in the _errorPort handler before calling `_failAll`, since errorsAreFatal means the isolate is about to exit. Or fail pending work only from the exit handler.

## [high] audio-android-focus-pause: pauseResume makes Android pause the meeting whenever audio focus is lost, and permanent focus loss pauses it until the user notices
- File: `lib/audio/audio_capture_service.dart:147`
- Scenario: `buildRecordConfig` sets `audioInterruption: AudioInterruptionMode.pauseResume` on every platform. In record_android 2.3, any value other than NONE makes AudioSessionManager.requestAudioFocus() take AUDIOFOCUS_GAIN (USAGE_MEDIA). AUDIOFOCUS_LOSS_TRANSIENT and AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK both call onFocusLoss, and AudioInterruptionPolicy turns that into Pause (AudioSessionManager.kt:122-131, AudioInterruptionPolicy.kt). So every notification sound or navigation prompt (they take GAIN_TRANSIENT_MAY_DUCK, which we see as CAN_DUCK) pauses capture while it plays, and that speech is lost. If someone opens a media app, plays a voice message or joins a Teams/Zoom call on the phone during a hybrid meeting, Android sends AUDIOFOCUS_LOSS. The library then abandons its focus request, so FocusRegained never arrives and the take stays paused until someone presses resume. Meanwhile the phone is lying on the table and the minutes silently miss the rest of the meeting. The comment at line 146 assumes only phone calls pause the take.
- Fix hint: On Android use AudioInterruptionMode.none, which skips the focus request: a meeting recorder should not yield to media or notifications, and Android already silences the mic during a real call. Keep pauseResume (or pause) for iOS only. Optionally show a clear warning when a system pause lasts more than a few seconds.

## [medium] audio-stale-selected-device: Selected input device is never cleared when it disappears, so the next session fails on Windows

## [medium] audio-ios-bluetooth-hfp-input: iOS allowBluetooth routes capture to a connected headset mic and misses the room

## [low] audio-android-ns-agc-on-asr-source: Android turns on NoiseSuppressor and AGC on top of the VOICE_RECOGNITION source

## [high] data-diarization-1: Resetting preferences deletes every voiceprint ledger stored in the settings table
- File: `lib/data/secure_settings.dart:410`
- Scenario: AppSettings.resetToDefaults() runs `_db.delete(_db.settings).go()` with no WHERE clause. ## [high] data-diarization-2: forgetVoice and merge leave the voiceprint ledger stale, so later corrections unlearn vectors that are not in the centroid
- File: `lib/data/repositories.dart:668`
- Scenario: forgetVoice clears the centroid and count but keeps every ledger entry `seg -> S` in every meeting. Example: S is enrolled from meeting M1 (ledger M1: s1..s10 -> S). The user picks 'this is not the same person' (forgetVoice). S is enrolled again from meeting M2 with count 2. ## [medium] data-diarization-3: A known speaker whose first segment opened an unlinked local cluster stays split from their voiceprint for the whole meeting
- File: `lib/diarization/speaker_tracker.dart:540`
- Scenario: Known speaker X starts talking and the first segment ties between voiceprints X (0.62) and Y (0.60). The tie path opens an unlinked cluster L, and the session links L to a new auto speaker Z (linkCluster). X is still 'unclaimed' (_unclaimedKnown only excludes ids linked to clusters), so every later segment of X is scored against both L (sim + 0.03 bonus) and X's voiceprint. These are the same person, so the margin is usually below 0.05. That makes the segment ambiguous, so L is never updated and its centroid stays frozen at the first segment. When X's voiceprint wins clearly, a second cluster linked to X is opened (matchedKnownSpeaker). The person is then split live between auto speaker Z and X, and the two clusters keep tying because neither gets updated. Nothing links an unlinked cluster to a voiceprint later on.
- Fix hint: When the tied candidates are an unlinked local cluster and a voiceprint that both pass their thresholds, link the cluster to that voiceprint (linkCluster), or let the local cluster absorb the segment. Alternatively, leave voiceprints that are highly similar to an existing local cluster out of the margin computation.

## [medium] data-diarization-4: Tiny-cluster cleanup merges distinct, even voiceprint-identified, speakers at centroid cosine 0.3 before linking
- File: `lib/diarization/clustering.dart:259`
- Scenario: _mergeTinyClusters runs before step 5 (linking) and compares cos(t.centroid, g.centroid) >= 0.3. For a single-segment cluster, cos(v, normalized centroid of g) = avgSim(v, g) / sqrt(selfSim(g)), which inflates the average linkage. With selfSim 0.5 and avgSim 0.22, the value is 0.31 and the merge happens. Example: known speaker Ahmed says 'موافق' for 1.5 s (cosine 0.8 to his voiceprint), and another person speaks for 20 s. Ahmed's segment falls under tinyClusterMaxMs, so it is absorbed into the other person's cluster and never reaches the Hungarian linking. The relabel attributes his statement to the wrong speaker, and learnFromCorrections then learns his embedding into that speaker's voiceprint. The same 0.3 (fallbackAttachThreshold) is used to attach deferred segments in long meetings.
- Fix hint: Link tiny clusters to voiceprints before merging them (or skip the merge when a tiny cluster passes linkThreshold against an unclaimed voiceprint). Base the merge on average linkage, or use a threshold of at least clusterThreshold.

## [low] data-diarization-5: The split-repair merge uses centroid cosine 0.4, which is weaker than the 0.5 average-linkage stop and can re-merge two different people
- File: `lib/diarization/clustering.dart:330`
- Scenario: Agglomerative clustering stopped because the average linkage between g and target was below 0.5. The repair step then merges them when cos(centroid_g, centroid_target) >= 0.4 and g's best voiceprint is the one target holds. Centroid cosine equals linkage / sqrt(selfSim_g * selfSim_target). For linkage 0.25 and intra-cluster sims of 0.6, that gives 0.42, so two clearly separated speakers are merged whenever both resemble X's voiceprint at >= linkThreshold (e.g. a family member or the same mic). The merged segments are relabeled to X and learned into X's voiceprint.
- Fix hint: Compare average linkage (sum . sum / (W_g W_t)) against clusterThreshold minus a small slack, or raise voiceprintMergeThreshold above clusterThreshold when using centroid cosine.

## [medium] minutes-1: TLS and socket errors skip the retry path and reach the user as a generic non-retryable error
- File: `lib/minutes/claude_client.dart:474`
- Scenario: package:http 1.6.0 IOClient.send (io_client.dart) converts only SocketException and HttpException into ClientException. A HandshakeException or TlsException thrown while the request is sent (captive portal, TLS-intercepting proxy, a handshake reset on mobile) is passed on unchanged. During the body, the response controller's onError wraps only HttpException; any other error (for example a raw SocketException 'Connection reset by peer' when the phone switches network during a 5-10 minute generation) is passed on as is. _attempt catches only TimeoutException and http.ClientException (lines 472-476), and _consumeStream catches TimeoutException, ClientException and FormatException (lines 656-668). These errors therefore skip _RetryableFailure, so none of the 4 attempts is used. post_processor._generate then wraps the error as MinutesGenerationException('تعذّر إنشاء المحضر.') with retryable=false, so a transient network blip loses the whole generation.
- Fix hint: In both _attempt and _consumeStream, also catch `IOException` (from dart:io, or check `e is IOException` behind a conditional import) and `TlsException`, and turn them into _RetryableFailure. One option is a catch-all for non-Insato errors that are not programming errors (`on Exception catch (e) when e is! InsatoException`).

## [low] minutes-2: Markdown escaping of ordered-list markers inserts a visible backslash before digits
- File: `lib/minutes/export_service.dart:125`
- Scenario: _mdText puts the backslash in front of the whole match `\d+[.)]`, so a line such as `3.5 مليون دولار` or `2026. عام` becomes `\3.5 مليون دولار` or `\2026. عام` (checked by running the same regex with dart). ## [low] minutes-4: A header timeout leaves the first request running on the server while a retry starts
- File: `lib/minutes/claude_client.dart:471`
- Scenario: `_client.send(request).timeout(idleTimeout)` only stops waiting for the future. The HTTP request keeps going and is never cancelled (no Abortable request or abortTrigger is used). If the server takes more than idleTimeout to send headers (for example, under the fallback beta a pre-output decline happens before message_start), the client throws _RetryableFailure and sends a second request. The first connection stays open and its stream is never listened to. The server may finish and bill that generation too, and the socket stays held until the owned client is closed.
- Fix hint: Use http.AbortableRequest with an abortTrigger completer and complete it on timeout. Alternatively, attach `.then((r) => r.stream.listen(null).cancel())` to the abandoned send future so the connection is drained and closed.
